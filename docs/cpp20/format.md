# `format`

`std::format` 以类型安全的占位符替代易错的格式化字符串和冗长的流状态设置。

```cpp example id="cpp20-format" std="c++20" file="main.cpp" kind="single" compilers="all" output="20 + 22 = 42"
#include <format>
#include <iostream>

int main() {
    std::cout << std::format("{} + {} = {}", 20, 22, 42) << '\n';
}
```

格式字符串在可行时接受编译期检查。若格式来自运行期输入，应使用对应运行期格式接口并处理错误。标准库对 `<format>` 的完整实现时间存在差异，验证矩阵会据实际工具链结果决定是否需要标记兼容边界。

## 格式字符串模型

替换字段使用 `{}`，可包含位置索引和格式说明。格式说明把对齐、宽度、填充、符号、精度和进制等策略与参数值分离。字面量中的花括号需要写成 `{{` 或 `}}`。

编译期已知格式字符串会通过 `basic_format_string` 一类接口检查参数数量和部分格式兼容性，许多错误在编译时暴露。运行期字符串无法获得同等静态保证，应通过对应运行期包装并处理 `format_error`。

字段的一般结构可理解为 `{arg-id:format-spec}`。arg-id 为空时按出现顺序自动编号；显式编号可复用或重排参数，但同一格式字符串不能混合自动编号与手动编号。冒号后规则由对应参数 formatter 解释。

```cpp example id="cpp20-format-specifiers" std="c++20" file="main.cpp" kind="single" compilers="all" output="hex=002a, fixed=3.50"
#include <format>
#include <iostream>

int main() {
    const std::string text = std::format(
        "hex={:04x}, fixed={:.2f}", 42, 3.5);
    std::cout << text << '\n';
}
```

`04x` 选择小写十六进制、宽度 4 并以零填充；`.2f` 选择定点表示和小数点后两位。格式说明属于每种类型的 formatter 契约，相同字符对字符串、整数和时间类型未必有相同合法含义。

### 通用格式项

常见选项包括填充与对齐、正负号、替代形式 `#`、零填充、最小宽度、动态宽度、精度和类型字符。宽度是最小输出宽度，不会截断更长结果；字符串精度可限制输出长度，浮点精度的含义依表示类型而变化。

动态宽度/精度可从另一个参数取得，其字段同样参与索引规则，且值类型/范围必须合法。协议输出应固定所需表示，避免默认浮点形式随数量级切换造成下游解析困难。

转义花括号只针对格式模板。参数字符串中的 `{`/`}` 是普通数据，不会被二次解析，这也是把不可信内容作为参数而非模板的重要安全边界。

对齐字符通常用 `<`、`>`、`^` 表示左、右、居中，填充字符写在对齐符之前。数值还存在符号感知与零填充规则，不能把字符串的“左侧补字符”直觉直接套用。不同类型只支持其 formatter 规定的 type 字符，非法组合产生格式错误。

显式参数编号允许同一参数重复出现，但重复格式化仍会执行相应 formatter，多次输出昂贵对象可能重复计算。自动编号的动态宽度参数也会推进编号序列，复杂模板最好采用显式编号或拆分成命名封装并增加测试。

格式宽度描述的是格式化协议认定的宽度，不保证等于终端显示列数。组合字符、全角字符、emoji 序列和 ANSI 控制码都会让“字符数量”“代码单元数量”“显示宽度”分离；表格终端 UI 需要 Unicode/终端专用测量。

## 类型安全与扩展

与 C 风格可变参数不同，`format` 保留每个参数静态类型，不依赖调用者手写 `%d`、`%s` 与实际类型保持一致。自定义类型可特化 `std::formatter<T, CharT>`，解析格式说明并把结果写入格式上下文。

格式化器应保持解析与输出职责分离，不在 `format` 中执行昂贵业务查询。公共库自定义格式需考虑字符类型、区域设置和异常保证。

`formatter<T, CharT>` 通常实现 `parse(format_parse_context&)` 与 `format(const T&, FormatContext&)`。parse 从冒号后开始读取类型专属说明并返回解析结束迭代器；format 把字符写到上下文输出迭代器并返回新位置。

自定义 formatter 位于 `std` 中的允许特化范围内，必须针对用户定义类型，并满足 BasicFormatter 要求。可以委托已有 formatter，例如先把领域对象映射成 `string_view` 或整数，再复用对齐/宽度逻辑，减少格式规则重复。

格式化不自动调用任意 `operator<<`。这让格式协议与流协议解耦，也意味着已有流输出类型不会天然可 format。库若同时支持二者，应让共同的无分配渲染核心服务两个前端。

编译期检查验证格式语法和静态参数类型，但不能证明运行期宽度合法、输出缓冲区足够或自定义 formatter 没有逻辑错误。自定义说明符需要单元测试非法输入和边界值。

`parse` 必须消费自己支持的说明并返回指向闭合 `}` 或规定位置的迭代器；悄悄忽略未知字符会让拼写错误无法诊断。无自定义说明时也要正确处理空范围。实现可在编译期调用 parse，因此解析代码需要满足相应 constexpr 使用要求。

`format` 通常声明为模板以接受不同 `FormatContext`，并通过 `context.out()` 获得输出迭代器。它不应假定目标是 `std::string` 或连续缓冲区。返回最终输出位置是协议的一部分，遗漏推进结果会破坏与其他字段组合。

格式器对象可能被实现复制，状态应只保存解析后的轻量选项，不应绑定某次参数对象地址。参数值由 `format` 调用传入，formatter 特化不拥有待格式化对象。

## 分配和输出

`std::format` 返回新字符串，因此通常需要分配足够缓冲区。写入既有输出迭代器可使用 `format_to`，预估长度可使用 `formatted_size`；高频日志还应评估日志框架缓冲与异步策略。

`format_to(out, fmt, args...)` 不拥有目标范围边界；若传入裸指针/不受限输出迭代器，调用方必须保证容量。`format_to_n` 最多写入指定数量字符，同时返回完整结果应有大小，适合固定缓冲区并检测截断。

`formatted_size` 计算若完整格式化会产生的字符数量，但仍需遍历格式逻辑，不是免费常量查询。先求大小再分配再 `format_to` 会执行两遍格式工作；`std::format` 或带增长缓冲的实现可能更适合一般场景。

标准接口按值捕获参数的类型信息并通过格式参数存储访问，格式化期间参数对象必须存活。不要保存 `format_args` 跨越其引用对象生命周期；需要延迟日志时，拥有地复制参数或预先完成格式化。

`make_format_args` 产生的参数存储通常引用传入对象而不延长生命周期。把它连同临时 `std::string` 放进异步队列会留下悬空引用，即使格式模板本身是静态字面量。延迟日志系统应拥有地保存类型擦除值，或在调用线程完成字符串渲染。

`format_to_n` 的返回结果包含最终输出迭代器和完整格式结果大小；当 size 大于限制时说明发生截断。输出缓冲区若要作为 C 字符串使用，还要自行预留并写入结尾零字符，格式算法只生成指定字符序列。

选择 `formatted_size` 后一次性分配可以避免增长重分配，却会执行一遍尺寸计算和一遍真实格式化。自定义 formatter 若输出依赖外部可变状态，两遍结果甚至可能不一致，因此 formatter 应尽量是对参数和解析选项的确定性纯渲染。

### `vformat` 与运行期模板

C++20 中运行期格式模板通常通过 `vformat` 配合 `make_format_args` 处理。它跳过 `basic_format_string` 的编译期模板检查，格式错误在运行期抛 `format_error`。后续标准增加了更便利的运行期格式包装，但不能用于最低 C++20 代码。

让最终用户编辑格式模板时，应限定可用参数、捕获 `format_error` 并设置输出长度上限。类型安全消除了 varargs 类型错配，不等于消除资源消耗或日志注入风险。

格式解析可能被编译器或库优化，但标准不承诺所有字面量零解析成本。与流、`snprintf` 的性能比较依赖参数类型和实现，需在目标标准库测量。

## 本地化与兼容性

默认格式化通常不使用全局 locale，带 locale 重载才应用本地化选项。日志和协议输出宜保持稳定、与区域无关；面向用户的数字和日期再显式选择区域规则。

`<format>` 虽属于 C++20，各标准库完整支持时间不同，项目必须在最低 GCC/Clang/MSVC 矩阵实际编译。示例验证证明当前 Apple Clang 环境已支持基础格式化。

默认数值表示与 locale 无关，适合机器日志和协议。带 locale 的重载只有在格式说明请求本地化形式时才应用相关规则；区域对象构造和 facet 查询也可能增加成本。

`std::format` 的时间格式支持与 `<chrono>` formatter、时区数据库实现成熟度相关，往往晚于基础整数/字符串格式。项目应按实际用到的类型逐项验证，不能以一个 `{}` 整数示例推断全部支持。

char 与 `wchar_t` 格式体系分别由字符类型参数化。标准 C++20 不直接提供任意 UTF-8 字形宽度排版保证；宽度/精度与 Unicode 显示列、组合字符之间存在实现和标准版本边界，终端 UI 需要专门文本库。

## 示例解析与实践

主示例三个 `{}` 按顺序取得整数，生成拥有的字符串再输出。工程中禁止把不可信输入直接当格式模板；复杂输出优先具名封装；热路径选择 `format_to` 并测量分配。

为日志封装保留格式字符串的编译期类型参数，避免先退化成 `string_view` 再传给 format，从而丢失静态检查。只有配置驱动模板才走 vformat 分支，并在边界统一处理异常。

测试应覆盖转义花括号、位置索引、负数、最大整数、负零、NaN/无穷、宽度不足、Unicode 数据和自定义 formatter 的非法说明。性能测试要把最终分配和输出 I/O 一并计算。

## 格式化接口速查

| 接口/语法 | 关键语义 |
| --- | --- |
| `{}` | 自动参数编号替换字段 |
| `{2}` | 显式参数编号；不能与自动编号混用 |
| `{{` / `}}` | 输出字面花括号 |
| `{:04x}` | 类型 formatter 解释的宽度/进制说明 |
| `format` | 返回拥有的 string，通常涉及分配 |
| `format_to` | 写输出迭代器，不自动检查裸缓冲区容量 |
| `format_to_n` | 限制写入数量并报告完整结果大小 |
| `formatted_size` | 计算完整字符数，仍会执行格式逻辑 |
| `vformat` | C++20 运行期模板路径，错误抛 `format_error` |
| `formatter<T>` | 用户类型允许的 std 特化，提供 parse/format |

## Format 专项审查问题

- 格式模板是编译期可信字面量还是运行期不可信输入？
- 自动编号和显式编号是否发生混用？
- 动态宽度/精度参数类型与范围是否验证？
- 自定义 formatter::parse 是否拒绝未知说明符？
- formatter 是否通过 context.out 工作而非假定 string 目标？
- `format_args` 是否越过其引用实参的生命周期保存？
- 固定缓冲区是否为结尾零字符额外预留空间？
- Unicode 显示列是否被错误等同于格式宽度？
- 延迟日志是否拥有参数，避免临时 string 悬空？
- `<format>` 的每种实际类型是否在最低标准库矩阵测试？

## Format 故障定位线索

- 编译期格式报错：先核对参数编号、花括号配对和类型说明符。
- 运行期抛 `format_error`：记录模板来源但避免原样回显敏感输入。
- 自定义格式器拒绝空说明：parse 没正确处理直接遇到 `}`。
- 后续字段错位：formatter::format 返回了错误输出迭代位置。
- 异步日志乱码/崩溃：`format_args` 引用了已经销毁的临时对象。
- 固定缓冲被截断：检查 `format_to_n` 返回的完整 size 而非只看写入数。
- C API 输出越界：格式结果不会自动替裸缓冲补零和扩容。
- 表格未对齐：Unicode 显示宽度不等于简单代码单元数量。
- `formatted_size` 与实际不一致：自定义 formatter 依赖了可变外部状态。
- 某标准库无法包含 format：支持进度晚于 C++20 前端语言开关。
