# Modules

## 学习目标与文本包含模型

C++17 头文件由预处理器逐个翻译单元文本展开，同一接口被重复解析，宏和包含顺序能够改变声明含义。预编译头可减少部分成本，却仍围绕文本环境工作，也没有语言级的导出边界。

C++20 Modules 用模块声明、`export` 和 `import` 表达语义依赖。接口被编译为工具链管理的模块产物，普通宏默认不随导入传播；但 Modules 不是包管理器，也不保证跨编译器发布稳定 BMI。

读完后，你应能区分主接口、实现单元、分区、全局/私有模块片段与 Header Unit，并为构建系统建立“扫描依赖—生成 BMI—编译对象—链接程序”的正确顺序。

## 最小语法

```text
export module geometry;       // 主接口单元
export double area(Circle);   // 导入方可见

module geometry;              // 实现单元
import geometry:detail;       // 导入分区

import geometry;              // 使用模块
```

## 第一个多文件示例

接口单元导出模块 `math` 和函数 `add`；调用程序只导入模块，不需要文本包含模块接口。

模块接口单元：

```cpp example id="cpp20-modules" std="c++20" file="math.cppm" kind="modules" compilers="gcc" output="42"
export module math;

export int add(int left, int right) {
    return left + right;
}
```

导入模块的程序：

```cpp example id="cpp20-modules" std="c++20" file="main.cpp" kind="modules" compilers="gcc" output="42"
import math;

#include <iostream>

int main() {
    std::cout << add(20, 22) << '\n';
}
```

程序输出 `42`。验证器在 GCC 任务中先以 `-fmodules-ts` 构建接口单元和 BMI，再编译、链接并运行调用程序。Apple Clang 与 GCC 的模块产物和命令行并不兼容，因此本例明确由 GCC CI 验证。

模块边界应围绕稳定接口设计；不要机械地把每个旧头文件一对一转换为模块。

## Modules 解决的根本问题

头文件通过预处理器文本包含，每个翻译单元重复解析同一声明，宏和包含顺序会影响含义。Modules 把接口作为编译后的语义实体导入，宏默认不跨模块边界传播，声明只在显式 `export` 后对导入方可见。

模块不是包管理器，也不决定源文件目录、依赖下载或二进制发布格式。BMI/CMI 通常与编译器版本、选项和目标平台紧密耦合，不适合作为长期通用二进制接口文件分发。

`import` 导入的是模块接口的语义结果，而不是在当前位置粘贴一份源文本。导入顺序不应像头文件顺序那样改变已导出声明的含义，导入方此前定义的普通宏也不会重写模块接口内部 token。

命名模块名称中的点只是命名约定的一部分，不自动建立层级关系。`company.graphics` 与 `company.graphics.image` 是两个独立模块，后者不会隐式导入前者。模块名也不必与文件名或目录结构一致，映射由构建系统/编译器配置负责。

Modules 优化的是声明传播和依赖隔离，不自动解决模板实例化成本、链接时间或运行时 ABI 稳定。导出的模板定义仍需对实例化可用，修改内联实现也可能使依赖 BMI 失效并触发重建。

## 声明顺序与模块片段

模块单元开头可以有全局模块片段：第一条是 `module;`，随后放置必须文本包含的传统头文件，之后才写模块声明。全局片段中的内容属于全局模块，不会因为位于同一文件就自动成为命名模块接口。

模块声明 `export module M;` 或 `module M;` 确定当前单元归属。声明之后可以导入依赖、定义模块内部实体并导出接口。主接口单元必须导出模块声明，模块实现单元不能重新导出主模块声明。

私有模块片段以 `module :private;` 开始，只能位于主接口单元的最后部分，用于让后续定义对其他模块单元也不可达。它适合少量实现隔离，但大型实现通常拆到独立实现单元更利于增量构建。

预处理条件仍可决定当前模块单元的源代码，但所有构建同一模块的单元必须使用兼容配置。宏不跨导入传播不等于模块内部可以随意用不同 ABI 宏编译。

### 模块 purview 与 import 位置

模块声明之后的声明位于相应模块 purview，之前全局模块片段中的声明不属于命名模块。一个实体归属哪个模块影响链接、ODR 和可达性，不能用源码文件恰好放在同一目录来推断。

模块单元中的 import 声明受顺序和区域限制，通常应紧随模块声明和其他 import，位于普通声明之前的 import 区域。把 import 像 `#include` 一样散落在函数体或命名空间内部不是合法替换策略。

`export import dependency;` 同时导入并重新导出依赖，使消费者导入当前模块时也能使用依赖的导出接口。普通 `import dependency;` 只供当前模块单元实现使用。公共 API 若暴露依赖类型，却没有让相应声明可达，会造成导入方无法完整理解接口。

## 单元与分区

主模块接口单元以 `export module name;` 声明并导出接口。模块实现单元使用 `module name;`，能访问模块内部声明但不重新导出。大型模块可拆成分区，并选择哪些分区由主接口重新导出。

全局模块片段允许在模块声明前包含传统头文件，私有模块片段可把实现限制在接口单元后部。迁移时必须区分文本头文件、header unit 和命名模块，它们的宏可见性不同。

### 主接口、接口分区和实现单元

一个命名模块恰有一个主模块接口单元。接口分区写成 `export module M:part;`，实现分区写成 `module M:part;`。分区只能被同一模块的单元以 `import :part;` 形式引用；外部消费者不能直接把分区名当公共模块随意导入。

主接口可用 `export import :part;` 重新导出接口分区。这样消费者只写 `import M;` 就获得所选分区的导出声明。没有被重新导出的接口内容不会因为构建在同一模块中自动成为公共 API。

实现单元 `module M;` 共享模块归属和对模块内部声明的访问能力，用于放置非内联函数定义、显式实例化等。它仍需在构建图中依赖主接口 BMI，但自身通常不产生供外部导入的新接口。

### 导出声明

`export` 可修饰单个声明，也可使用 `export { ... }` 块导出一组声明。只有具有适当名称和可导出性质的声明才能导出；内部链接实体、匿名命名空间内容等不能借 `export` 变成外部公共接口。

导出函数的签名若暴露未导出类型，导入方可能无法使用接口。模块边界要从整个可达类型图审查，不只检查函数名是否写了 `export`。模板、默认参数、基类和返回类型都会把依赖带入接口。

“可见”与“可达”需要区分：名字可见决定普通名称查找能否找到声明，可达性决定某个已找到/导出实体的语义依赖是否可供编译器使用。导入方未必能直接按名字引用所有实现依赖，但实例化导出模板时需要的声明仍必须按模块规则可达。

导出模板尤其容易把依赖泄漏到接口：约束、默认模板实参、requires-expression、内联成员体和 ADL 候选都可能需要相关声明。只把模板名称放进 `export {}` 而把必要类型留在不可达实现区，会在消费者实例化时失败。

导出 using-declaration 或别名不会自动把一个本来不可导出的实体变成独立复制品，它仍指向原实体及其模块归属。迁移 façade 头时，应验证重导出链而不是假定别名能绕过边界。

## 构建图与 BMI

编译器必须先处理被导入模块的接口并生成 BMI，再编译导入者，因此构建系统需要扫描 import 依赖并按拓扑顺序调度。与头文件依赖只靠时间戳不同，Modules 需要理解编译命令、模块名到源文件/BMI 的映射。

示例验证器先编译 `math.cppm`，生成 GCC 模块缓存和对象文件，然后编译导入者并链接。Clang、GCC、MSVC 的命令、扩展名和缓存管理不同，这也是必须由构建系统封装的原因。

### 扫描、编译和链接是不同阶段

依赖扫描要先识别每个源文件提供和需要的模块名，构建 BMI 的拓扑顺序，再安排普通对象编译。接口单元往往同时产生 BMI 和对象文件：BMI 服务编译期语义导入，对象文件仍服务最终链接。

只删除对象文件却保留过期 BMI，或复用由不同宏、语言选项、标准库模式生成的 BMI，都可能产生编译错误甚至更隐蔽的不一致。构建缓存键至少要纳入编译器版本、目标三元组、语言模式和影响接口的选项。

循环模块导入无法像互相包含头文件那样靠 include guard 勉强通过。模块依赖图需要可拓扑排序；出现概念循环时应抽取共同接口、重划模块边界或使用实现层反转依赖。

构建系统还要协调并行生成：多个任务不能无规则地同时写同一 BMI 缓存。手写 shell 命令适合教学验证，不适合大型仓库的增量依赖管理。

### BMI 不是稳定发布物

标准没有规定 BMI 文件格式。不同编译器、同一编译器不同版本乃至不同编译选项通常互不兼容。发布库时仍应提供源接口或与消费者工具链严格匹配的构建产物，不能把 BMI 当成类似平台稳定共享库的通用格式。

## 可见性、链接与 ODR

未导出声明可供同一模块的实现单元使用，却不会进入导入方名称查找。导出并不等同于动态库符号导出；共享库可见性和 ABI 仍需平台属性与构建配置。

模块能减少因重复文本定义产生的 ODR 风险，但同一程序混用头文件声明与模块声明仍可能制造实体归属问题。迁移必须从依赖图和第三方兼容性出发逐步进行。

模块 linkage、语言 linkage 和共享库符号 visibility 是不同层次。`export` 只控制导入方的语言可见性；若构建 DLL/DSO，仍需处理平台导出表、调用约定、版本兼容和隐藏符号策略。

命名模块中的某些非导出声明具有模块链接语义，可供同一模块的其他单元使用，却不会与其他模块中同名声明合并。这个隔离减少全局名字碰撞，但也意味着把原头文件声明迁入模块会改变实体归属，不能同时保留两套未经协调的定义。

模块内定义的类、内联函数和模板仍受相应 ODR 约束。Modules 让编译器更清楚实体来源，并不授权不同分区给同一实体提供不一致定义。

### 附着到模块的实体

模块声明之后定义的实体通常附着到该命名模块。它们与全局模块中源码文本相同的声明不一定表示同一实体，这正是混合迁移会出现重复定义或不一致链接的根源。必须让传统头入口和模块入口有明确的单一事实来源。

语言链接 `extern "C"` 主要控制名称和调用约定相关规则，并不会自动取消声明的模块归属。共享 C API 的迁移要在目标编译器上验证模块附着、符号导出与旧消费者链接，而不能仅看最终符号名相似。

不同模块可以拥有未导出的同名内部实体而互不冲突，但公共签名若通过类型别名或模板参数意外引用各自内部类型，二者仍是不同类型。模块隔离减少名字碰撞，也让过去依赖全局合并的代码需要显式重构。

## Header units 与宏

Header unit 允许以 `import <header>;` 或实现支持的形式把传统头文件作为预编译语义单元导入。哪些头文件可作为 header unit、如何构建映射以及标准库支持程度依赖工具链。

从 header unit 导入的宏可见性与命名模块不同，标准及实现迁移细节较复杂。依赖“包含某头后获得配置宏”的旧代码不能机械替换为 import；配置宏往往要留在文本包含边界，或重构为真正的常量/接口。

`#include` 的同一头和 header unit 混用可能造成重复实体、宏状态和构建缓存问题。项目应制定单一迁移策略，并让构建系统决定某依赖走文本、header unit 还是命名模块。

## ABI、封装与重编译

未导出实现细节不会进入导入方普通名称查找，但导出类的布局、内联函数体、模板定义和默认参数仍可能把实现细节编码进消费者。想获得稳定 ABI，仍要采用 PImpl、版本化接口、固定布局或 C 边界等传统设计。

修改非导出实现单元通常只需重编该对象；修改模块接口会使导入者 BMI 依赖失效。合理拆分稳定接口和高频变化实现，才能兑现增量构建收益。把所有实现塞进主接口单元会重新制造大面积重建。

## 工程迁移策略

先选择宏依赖少、接口稳定的叶子库试点；确保构建系统原生支持依赖扫描；固定编译器工具链与缓存失效策略；测量干净构建和增量构建；保留非模块消费者需要的兼容入口，避免一次性转换整个代码库。

迁移前先列出：公共声明、配置宏、平台条件、生成头、循环依赖、显式实例化和共享库导出宏。宏型 API 要先重构，因为命名模块有意不把宏作为接口机制。

兼容头可以暂时转发到旧声明或在支持时导入模块，但必须保证头消费者和模块消费者最终引用同一实体。不要简单复制声明到两个世界。构建矩阵应覆盖纯头文件、纯模块以及允许的混合链接方式。

CI 除干净构建外还应测试增量场景：只改实现是否避免重编消费者、改接口是否正确触发、切换编译选项是否使 BMI 失效、并行构建是否无竞态。缓存错误往往只在增量构建暴露。

## 当前工具链边界

GCC 的 `-fmodules-ts`、Clang 的标准 C++ Modules 驱动方式与 MSVC 流程在文件识别、BMI 路径和标准库 header unit 上都有差异。项目文档应记录精确编译器版本与构建命令，而不是只写“支持 C++20”。

本仓库的示例刻意使用最小接口单元和导入者，并在 GCC CI 真实生成模块缓存、对象、可执行文件再运行。它验证语言链路，但不代表生产构建系统、分区和第三方依赖已具备可移植方案。

## 模块单元速查

| 声明 | 单元/可见性语义 |
| --- | --- |
| `export module M;` | 主接口或接口单元的导出模块声明 |
| `module M;` | M 的实现单元 |
| `export module M:P;` | 接口分区 |
| `module M:P;` | 实现分区 |
| `import M;` | 导入 M 的导出接口供当前单元使用 |
| `import :P;` | 同一模块内部导入分区 |
| `export import M;` | 导入并向消费者重新导出依赖 |
| `module;` | 开启全局模块片段，通常放传统 include |
| `module :private;` | 主接口末尾的私有模块片段 |
| `export { ... }` | 导出一组满足可导出规则的声明 |
| BMI/CMI | 编译器私有构建产物，不是标准稳定分发格式 |

## Modules 专项审查问题

- 模块名到源文件/BMI 的映射是否由构建系统统一管理？
- import 依赖图是否无环并能拓扑构建？
- 导出签名涉及的类型、约束和模板依赖是否全部可达？
- 传统宏接口是否已重构，而非期待命名模块导出宏？
- 头文件入口和模块入口是否最终引用同一实体？
- BMI 缓存键是否包含编译器版本、目标、语言和 ABI 选项？
- 修改接口能否让所有导入者正确失效重建？
- 修改实现单元是否避免无谓重编消费者？
- `export` 与共享库符号可见性是否被分别配置？
- GCC/Clang/MSVC 的命令差异是否由 CI 实际覆盖？

## Modules 构建故障定位线索

- 找不到模块：检查提供者是否先生成 BMI 及名称映射一致。
- BMI 版本错误：清理并按当前编译器/选项重建缓存。
- 导入后名字不可见：确认声明本身已 export 或经 export import 重导出。
- 模板在消费者实例化失败：检查依赖声明可达性而非仅名称导出。
- 增量构建出现幽灵错误：核对 BMI 缓存键和接口失效依赖。
- 相同声明重复定义：检查头文件入口与模块入口是否复制了实体。
- 宏配置不生效：命名模块有意隔离导入方普通宏。
- 链接仍缺符号：BMI 只服务编译期，确认接口单元对象也参与链接。
- 并行构建竞态：确保同一 BMI 只有一个受调度的生成任务。
- 仅一台机器失败：记录编译器补丁版本、标准库和完整模块命令行。
