# 指定初始化

指定初始化用成员名初始化聚合对象，配置结构体因此更易读，也不再依赖读者记住每个值的位置。

<!-- example id="cpp20-designated-initialization" std="c++20" file="main.cpp" kind="single" compilers="all" output="localhost:8080 secure=false" -->
```cpp
#include <iostream>
#include <string>

struct ServerConfig {
    std::string host;
    int port = 80;
    bool secure = false;
};

int main() {
    const ServerConfig config{
        .host = "localhost",
        .port = 8080,
        .secure = false,
    };
    std::cout << config.host << ':' << config.port
              << " secure=" << std::boolalpha << config.secure << '\n';
}
```

C++20 要求指示符遵循成员声明顺序，且只适用于聚合类型；它不同于允许任意顺序的某些语言扩展。

## 聚合类型前提

指定初始化建立在聚合初始化之上。聚合大致是允许成员直接按声明结构初始化的数组或类，不能具有破坏聚合条件的用户声明构造函数等特征；精确定义随标准演进。给配置结构新增构造函数可能让已有指定初始化调用全部失效。

每个指示符必须命名当前类的直接非静态数据成员，不能指定基类成员、嵌套路径或同一成员两次。未指定成员按默认成员初始化器初始化，否则执行空列表初始化。

<!-- example id="cpp20-nested-designated-init" std="c++20" file="main.cpp" kind="single" compilers="all" output="api.example:80 verify=true" -->
```cpp
#include <iostream>
#include <string>

struct TlsConfig {
    bool enabled = true;
    bool verify_peer = true;
};

struct ClientConfig {
    std::string host;
    int port = 80;
    TlsConfig tls;
};

int main() {
    const ClientConfig config{
        .host = "api.example",
        .tls = {.verify_peer = true},
    };

    std::cout << config.host << ':' << config.port
              << " verify=" << std::boolalpha << config.tls.verify_peer << '\n';
}
```

外层跳过 `port`，因此使用默认成员初始化器 80；随后指定 `tls`，其初始化器内部又对 `TlsConfig` 做一次独立指定初始化。C++ 不支持 C 风格的 `.tls.verify_peer = true` 嵌套指示符，必须在被指定成员的花括号里开始新的聚合初始化。

### C++20 聚合规则边界

指定初始化只适用于类聚合，不适用于数组的下标指示符。C++ 不支持 `[3] = value`、混合位置/指定初始化，也不支持任意顺序。这些写法可能被某些编译器以 C 扩展接受，使用 `-pedantic` 能帮助发现不可移植代码。

成员必须是当前聚合的直接非静态数据成员。基类子对象虽参与普通聚合初始化，却不能用 `.Base = ...` 指定；匿名联合的指定初始化还有专门限制，一次只能选择相应成员。

位域可以按成员名指定，只要初始化值满足其类型/宽度规则。引用成员若既未指定也没有默认成员初始化器，空列表初始化无法提供绑定，程序不合法。

### 联合与匿名联合

联合聚合的指定初始化可以选择一个非静态数据成员，从而明确哪个成员成为活动成员；不能同时指定两个成员。未指定联合且没有默认成员初始化器时，空列表初始化的活动成员规则需按聚合条款理解，业务代码更宜显式选择。

聚合中包含匿名联合时，designator 命名的是匿名联合内部的成员，而不是一个不存在的匿名联合对象名，并且同样只能选择一个。联合活动成员切换、非平凡成员析构和读取非活动成员仍遵守普通联合规则，指定语法不会提供 variant 式判别标签。

指定初始化不能为数组指定下标，也不能直接穿透成员数组设置某一项。可以把整个数组成员指定为花括号列表；若需要稀疏索引配置，应使用 `std::array` 构建函数或运行期赋值，而不是依赖编译器 C 扩展。

## 顺序要求的原因

C++ 对象成员始终按声明顺序初始化，而不是按初始化列表书写顺序。C++20 要求指示符也保持声明顺序，避免源码顺序与真实构造顺序产生错觉，并简化聚合初始化模型。

这意味着在结构体中间插入新成员通常不破坏只指定前后兼容顺序的调用，但移动成员声明可能导致编译错误。配置类型的成员顺序因此也成为一定程度的源代码接口。

允许跳过成员，但已写出的 designator 序列必须是声明顺序的子序列。若声明为 `host, port, tls`，写 `.host` 后可直接写 `.tls`，却不能再回头写 `.port`。

实际初始化仍严格按成员声明顺序进行，默认成员初始化器也在相应位置求值。这保证某个后置成员的默认值可以按普通规则引用更早已初始化状态，却不能安全依赖后置成员。

成员重排不仅影响指定初始化源码，还可能改变对象布局、默认比较顺序和 ABI。把配置聚合作为公开 API 时，应像维护函数参数结构一样审查成员演进。

每个显式初始化器表达式也按聚合元素的初始化顺序求值，而非编译器先收集全部右值再赋字段。若初始化表达式之间共享可变状态，顺序虽可预测，却会让配置声明难以理解；字段值应尽量独立计算。

默认成员初始化器只在该成员未被显式指定时使用。即使显式值与默认值文本相同，仍走显式初始化表达式；默认初始化器中的副作用不会执行。默认值应保持无副作用，否则调用点是否指定字段会暗中改变全局行为。

基类子对象按聚合顺序先于派生成员初始化，但 C++20 designator 不能命名基类。含聚合基类的复杂配置若需要只设置部分基类字段，只能通过相应基类整体的普通位置初始化，调用点可读性会迅速下降，通常应改为组合成员。

## 默认值与演进

指定初始化很适合带合理默认值的参数对象：调用点只写与默认不同的字段，比长位置参数清晰。新增带默认值的尾部成员通常兼容，新增必须设置却无类型级约束的字段可能被旧调用静默遗漏。

若必须保证某字段存在，应使用构造函数、工厂或强类型构建器，而不是仅依赖代码审查发现未指定成员。

没有默认成员初始化器的标量成员在被省略后执行空列表初始化，通常得到零；类成员执行相应空列表初始化。零值未必是安全业务默认，例如端口 0、空超时和空指针可能有完全不同语义。显式写出领域默认比依赖值初始化更易审查。

指定初始化不能验证字段之间的关系，例如最小值不大于最大值、启用 TLS 时证书路径必须存在。聚合适合“字段独立且默认安全”的数据载体；需要跨字段不变量时，用验证工厂返回错误，或改用构造函数封装有效状态。

新增带安全默认的尾部成员通常对现有调用友好。删除/重命名成员会直接编译失败，反而容易发现；改变默认值则可能静默改变所有省略该字段的调用，必须作为行为兼容性变更记录。

## 与构造函数和 Builder 的取舍

指定初始化带来调用点字段名和零额外运行时成本，但要求保持聚合。用户声明构造函数、私有数据加 setter、继承层不变量等封装需求会退出这种模型。

构造函数适合少量必填值和强不变量；具名工厂适合解析/验证可能失败；Builder 适合大量可选项、任意设置顺序和最终统一验证。不要为了保留 `.field =` 语法把本应私有的不变量暴露为公共成员。

配置文件反序列化仍需字段映射库或手写解析，指定初始化本身没有运行期字段元数据。字段名也不会进入二进制，改名影响源码而非自动迁移持久化格式。

指定初始化还会把公共成员名固化为源码 API：调用者直接写 `.retry_count`，重命名无法由仅保留同签名构造函数的兼容层吸收。对长期稳定 SDK，具名工厂/Builder 可以在内部改字段布局并保留旧方法；对仓库内部简单配置，编译失败式迁移反而很有价值。

聚合状态没有“构造完成后统一验证”的自动钩子。可以提供独立 `validate(config)`，但调用者可能忘记；如果无效状态会引发安全或资源问题，应让构造路径返回只能表示有效状态的封装类型，而不是为了语法便利保留公共聚合。

## 底层与成本

它只是初始化语法，不保存字段名或运行期映射。编译器仍按普通成员布局直接构造，通常没有额外成本。字段名提升的是源代码可读性，不提供反射或序列化能力。

## 示例解析与实践

示例按声明顺序设置三个字段。工程中保持配置聚合简单、提供安全默认、避免成员重排，并用测试验证默认组合；需要复杂不变量时升级为构造函数或具名工厂。
