# 二进制字面量与数字分隔符

## 学习目标与旧写法的问题

C++11 已支持十进制、八进制和十六进制整数，但位协议常要把十六进制值在脑中转换成二进制；长数字也只能依赖注释或人为数位统计。C++14 增加二进制字面量和数字分隔符，只改善源码表达，不改变运行时数值模型。

读完后，你应该能够正确书写 `0b`/`0B` 字面量，在整数和浮点数字中使用单引号分组，并判断字面量最终类型、整数提升和移位边界。

## 最小语法

```text
unsigned permissions = 0b1101'0010;
long population = 1'000'000;
double distance = 12'345.678'9;
```

分隔符必须位于数字序列内部，不得紧邻前缀、小数点、指数标记或类型后缀。

## 第一个完整示例

二进制常量按四位分组展示掩码，十进制常量按千位分组展示人口数量。

```cpp example id="cpp14-literals" std="c++14" file="main.cpp" kind="single" compilers="all" output="mask=165, population=1000000"
#include <iostream>

int main() {
    const unsigned mask = 0b1010'0101;
    const int population = 1'000'000;
    std::cout << "mask=" << mask << ", population=" << population << '\n';
}
```

程序输出 `mask=165, population=1000000`。分隔符不会进入数值，也不会影响输出格式；位操作仍应优先使用足够宽的无符号类型，避免有符号移位和整数提升带来的边界问题。

## 词法与类型规则

二进制字面量以前缀 `0b` 或 `0B` 开始，之后只能出现二进制数字和合法分隔符。它与十六进制、八进制字面量一样先形成整数常量，再根据数值、进制和后缀规则选择能表示该值的整数类型。

单引号只是词法分隔符，不进入数值，也不要求固定分组。`0b1010'0101` 按半字节分组便于与十六进制对照，`1'000'000` 按千位分组便于阅读。分组应服务于领域含义，位字段可以按协议段而非四位分组。

整数字面量的候选类型序列受进制影响。无后缀十进制通常依次尝试 int、long、long long；二进制/八进制/十六进制还会在候选中穿插相应无符号类型。因此同一巨大数值用十进制和二进制书写时，最终类型不一定相同。

后缀 `u/U`、`l/L`、`ll/LL` 可组合控制候选集合，但仍应避免依赖 long 的平台位宽。要求恰好 32/64 位时，用 `<cstdint>` 固定宽度类型并检查存在性，或用 `UINT32_C` 等宏构造适合类型的常量。

分隔符属于 preprocessing number 的词法，必须位于数字序列内部。它与用户定义字面量后缀共享单引号附近的词法历史，格式化工具应按 C++14 语法处理，不能把所有单引号都当字符字面量边界。

### 整数提升仍然存在

即使把字面量赋给 `uint8_t`，参与 `~`、移位和算术时通常先进行整数提升到 int。`~std::uint8_t{0}` 的直接结果类型往往不是 `uint8_t`，截断回目标宽度前高位会参与表达式。

位掩码表达式应让操作数使用足够宽的无符号类型，并在最终窄化时显式转换。二进制字面量只改变源代码基数，不关闭 usual arithmetic conversions。

## 编译器与运行时成本

词法分析阶段会忽略合法分隔符，并把不同进制文本解析成同一整数值。目标代码中不存在“二进制字面量格式”，因此不会产生额外运行成本，也不会让输出自动变成二进制格式。

位掩码的类型仍然重要。没有后缀的较大字面量可能推导成实现相关的有符号或无符号整数类型；需要精确宽度时使用 `UINT32_C`、固定宽度类型转换或合适后缀，并检查目标类型是否存在。

调试器和反汇编器可按自己的格式显示同一值，源代码的分隔位置不会进入对象文件语义。若运行期输出要保持字段分组，需要格式化函数单独实现。

编译器对字面量做范围检查；超出所有候选整数类型可能诊断或涉及扩展整数类型。不要用超大未后缀字面量再指望赋值目标类型“截断成想要结果”。

数字分隔符不会改善浮点精度。十进制 token 仍按目标类型转换和舍入，长于类型有效数字的尾部只是帮助记录精确十进制意图，不能让 double 保存全部数字。

## 常见错误与实践

- `0b` 是数字零加字母 b，不是字母 O。
- 分隔符不能连续出现，也不能紧邻前缀、后缀、小数点或指数标记。
- 二进制书写不会自动防止移位越界和整数提升。
- 协议位字段建议同时定义具名掩码、位位置和静态断言，而不是在业务代码散落魔法数字。

分隔符之后紧跟标识符字符时还要考虑字面量后缀 token。团队格式规则应固定千分位、半字节或字段式分组，避免同一常量被不同作者任意分割。

权限、寄存器和协议常量建议用 enum class 表达字段，再提供显式底层位运算辅助；二进制字面量用于定义层，业务层读具名枚举。这样字段变化集中在一处。

对掩码写 `static_assert`：字段不重叠、组合不超过底层位宽、保留位为零。分隔符是给人看的边界，断言才是编译器检查的边界。

示例中的两个字面量在编译后分别就是整数 165 与 1000000；其价值完全在源代码可读性和审查准确度。

## 位字段的可读分组

二进制字面量可以按协议字段而不是固定四位分组。数字分隔符不改变值，因此可以用分组直接展示版本位、权限位和标志位的边界。配合无符号类型可避免符号扩展影响右移。

```cpp example id="cpp14-binary-bit-fields" std="c++14" file="main.cpp" kind="single" compilers="all" output="read=true, write=false, version=5"
#include <cstdint>
#include <iostream>

int main() {
    const std::uint8_t packet = 0b101'0'1;
    const bool readable = (packet & 0b0'0'1) != 0;
    const bool writable = (packet & 0b0'1'0) != 0;
    const unsigned version = static_cast<unsigned>(packet >> 2);

    std::cout << std::boolalpha
              << "read=" << readable
              << ", write=" << writable
              << ", version=" << version << '\n';
}
```

这里最低两位表示权限，其余高位表示版本。真实协议应同时定义掩码和移位常量，并静态断言字段不会重叠；字面量的分组只提高可读性，不能代替这些不变量。

## 浮点数字分隔

分隔符也能出现在浮点数字序列和指数数字中，例如 `6.022'140'76e23`。它不改变舍入到目标浮点类型的过程。需要十进制精确语义的金融数据仍不应因为字面量更清晰就直接使用二进制浮点。

可以在十六进制整数字面量中分隔数字；十六进制浮点字面量是 C++17 特性，不应因为 C++14 有数字分隔符就把 `0x1.fp3` 归入本页最低版本。版本归属要区分“分隔语法可用”和“字面量类别本身可用”。

指数的符号与数字之间不能插入分隔符，分隔符也不能直接挨小数点。合法示意可写成 `1'234.5'678e1'0`，实际分组应服务科学量的有效数字或单位习惯。

金融/十进制定点可把缩放后的整数写成 `12'345'67` 等领域分组，但最好封装强类型和单位，避免读者误解小数位置。源代码分组没有运行期缩放语义。

## Token、类型与可移植边界

### 字面量速查

| 写法 | 含义或边界 |
| --- | --- |
| `0b1010` / `0B1010` | 二进制整数字面量，值为十进制 10 |
| `0b1010u` | 使用 unsigned 后缀参与候选类型选择 |
| `1'000'000` | 单引号仅为分组，值与无分隔符相同 |
| `0b1111'0000` | 可按半字节分组，不记录分组元数据 |
| `1'000.25` | 浮点整数部分允许分隔 |
| `1.0e1'0` | 指数数字序列允许分隔 |
| `0b'1010` | 分隔符紧贴前缀，不是合法标准写法 |
| `1.'0` | 分隔符紧贴小数点，不合法 |
| `1e+'10` | 分隔符紧贴指数符号，不合法 |
| 十六进制浮点 | C++17 能力，不属于最低 C++14 契约 |

整数字面量的候选类型仍由进制、数值和后缀共同决定。无后缀的二进制/八进制/十六进制字面量与十进制候选列表不完全相同，位掩码宜显式使用 `u`/`ull` 后缀并赋给经审查的无符号类型。

分隔符不能紧贴进制前缀、类型后缀、小数点、指数标记或指数正负号，也不能成为数字序列首尾。它属于词法 token 的一部分，但不进入最终数值和调试表示。

浮点分隔只改善源码阅读，不改变从十进制文本到 float/double/long double 的舍入。大量书写位数不会让目标类型获得额外精度。

十六进制浮点字面量到 C++17 才标准化，不能因 C++14 有二进制整数字面量就把两者混为同期能力。宏拼接数字片段还容易破坏 token 化，优先直接写完整字面量或 constexpr 构造接口。

## 字面量专项审查

- 位掩码是否带合适无符号后缀？
- 值是否超出候选整数字面量类型范围？
- 分隔符是否位于合法数字序列内部？
- 分组是否与协议位宽一致而非造成视觉误导？
- 浮点分隔是否被误认为增加精度？
- 宏拼接是否破坏预处理 token？
- 编译器是否仅以扩展接受非法分隔位置？
- 是否启用 pedantic 捕捉非标准写法？
- 是否误用尚属 C++17 的十六进制浮点能力？
- 序列化是否独立于源码分隔分组？
