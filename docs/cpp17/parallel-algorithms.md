# 带执行策略的算法

阅读前建议先了解：[迭代器与算法](../prerequisites.md#迭代器与算法)、[C++11 并发](../cpp11/concurrency.md)。本篇介绍的新增能力属于 C++17；后续版本差异会另行标注。

## 学习目标与并行化契约

C++14 标准算法只提供不带执行策略的重载。项目若想并行处理元素，需要自行分块、创建任务、汇总结果和传播错误。C++17 为部分算法增加执行策略重载，并加入适合重新分组计算的归约与扫描算法。

策略不是“加一个参数就自动更快”的开关，而是一份放宽执行顺序的契约：调用方必须保证元素操作在线程安全、异常、前进保证和数值结合性方面满足所选策略。实现仍可因数据规模或后端能力选择顺序执行。

读完后，你应能区分 `seq`、`par` 和 `par_unseq`，审查回调副作用，理解 `reduce` 与 `accumulate` 的语义差异，并用基准和工具链矩阵决定是否采用。

## 最小接口

```text
std::sort(std::execution::par, first, last);
std::transform(std::execution::par_unseq, first, last, output, operation);
std::reduce(std::execution::par, first, last, initial, operation);
```

只有明确提供策略重载的算法才能这样调用；策略允许某种执行方式，不承诺线程数量。

## 执行策略不会改变正确性要求

以下片段只对比写法；完整、可运行的程序见后文。

```text
// 传统顺序调用
std::sort(values.begin(), values.end());
// C++17：允许按策略执行
std::sort(std::execution::par, values.begin(), values.end());
```

对于满足算法前置条件的比较器，两种调用都应得到满足排序关系的结果；等价元素顺序并无稳定保证。par 允许并行，不保证一定开线程或更快。适合数据量大、回调可安全并发的独立工作；小任务、共享可变状态或需要特定异常恢复的流程应谨慎选用。

## 第一个完整示例与工具链说明

验证示例有意使用 `seq`，先展示策略重载的形状并保持确定输出。将它改为并行策略之前，必须重新审查 Lambda 的所有共享状态和异常路径。

```cpp example id="cpp17-execution-policies" std="c++17" file="main.cpp" kind="single" compilers="gcc" output="1 4 9 16"
#include <algorithm>
#include <execution>
#include <iostream>
#include <vector>

int main() {
    std::vector<int> values{1, 2, 3, 4};
    std::transform(std::execution::seq, values.begin(), values.end(), values.begin(),
                   [](int value) { return value * value; });
    for (const int value : values) {
        std::cout << value << (value == values.back() ? '\n' : ' ');
    }
}
```

程序输出 `1 4 9 16`。输入与输出范围相同是该 `transform` 形式允许的用法，每次调用只读写当前元素。替换为并行策略前，回调必须避免数据竞争、锁顺序问题和对执行顺序的依赖；实际收益需通过基准测试确认。

该示例由 CI 的 GCC/libstdc++ 任务验证。部分 libc++ 发行版本尚未提供标准执行策略，因此 Apple Clang 验证任务会明确跳过本例。

## 执行策略的语义

`sequenced_policy` 保证调用在当前线程按顺序执行。`parallel_policy` 允许在多个线程并行，但同一线程内调用不交错。`parallel_unsequenced_policy` 还允许向量化或线程内无序交错，因此回调不能执行不适合向量化的同步操作。

策略是“允许实现采用某种执行方式”，不是线程数量承诺。小输入、资源不足或实现限制都可能退回顺序执行。调用方不能通过观察线程 ID 推导正确性。

策略对象定义在 `<execution>`：`execution::seq`、`execution::par` 和 `execution::par_unseq` 分别是对应策略类型的全局对象。算法是否接受某个自定义策略，由标准的执行策略识别规则决定；普通业务标签不能仅靠形似接口成为标准策略。

并非所有标准算法都获得策略重载。C++17 为一批算法和数值算法增加重载，并引入 `reduce`、`transform_reduce`、包含式/排除式扫描等适合并行分解的设施。使用前应核对具体函数签名、迭代器类别和操作要求，而不是简单在任意算法第一个参数前加 `par`。

### 三种执行保证

`seq` 的函数对象调用在调用线程中有顺序地执行，最接近传统算法，但仍应按该算法本身的契约理解次序。`par` 允许不同线程并发调用，单个线程内的调用保持顺序关系。`par_unseq` 还允许调用在同一线程中无顺序交错，并为向量化开放空间。

因此 `par_unseq` 的元素函数不能调用依赖普通阻塞同步或其他 vectorization-unsafe（不适合无序交错执行）操作。一次调用若持锁后被挂起，同线程交错执行的另一次调用可能再次等待该锁，形成无法前进的情况。动态分配还可能拖慢热循环，但 C++17 的 vectorization-unsafe 定义对内存分配/释放函数有例外，不能直接概括为“所有动态分配都被禁止”；自定义分配器里其他同步操作仍需审查。全局流输出与无同步的共享随机引擎也不适合这类回调。[并行算法规范提案](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2016/p0024r2.html)

标准策略不保证开启新线程，也不保证每个元素在哪个线程执行。线程局部变量可能被不同元素复用，不能作为元素身份或稳定分区编号。

## 异常与终止

标准执行策略重载中的用户函数若抛异常，许多规定场景会调用 `std::terminate`，与普通无策略算法的异常传播不同。并行回调应把错误编码进结果或使用不会抛出的操作，并查阅具体算法和策略规则。

对于标准定义的策略，元素访问函数抛出的未捕获异常会导致 `terminate`；实现为算法自身分配内存失败可以抛 `bad_alloc`。这意味着简单地在调用并行算法的外层写 `try/catch`，通常捕获不到回调中的业务异常。

可恢复错误可以先在回调内部捕获，再写入预先设计的线程安全结果，例如原子失败标志和按元素独立的错误槽。但并行算法没有通用的协作取消保证：设置失败标志后，其他已经调度的调用仍可能执行。若业务要求首错立即停止、精确清理或异常聚合，显式任务系统可能更合适。

## 数据竞争与副作用

算法可以并发调用函数对象副本。不同迭代元素若写入共享计数器、日志容器或随机引擎，会产生竞争或锁瓶颈。安全模式是让每次调用只访问当前元素，或使用经过证明的归约算法和关联操作。

浮点加法不满足严格结合律，并行归约改变组合顺序后结果可能与顺序版本有微小差异。确定性和数值误差必须作为接口要求单独评估。

两个并行调用即便处理不同索引，也可能通过别名访问同一对象。原地 `transform` 等算法只有在标准接口允许相应输入输出重叠时才安全；额外捕获的引用则由程序员负责证明独立性。

普通计数累加不是原子操作。改成原子可以消除数据竞争，却可能让所有工作竞争同一缓存行并抹掉并行收益。优先使用 `reduce`/`transform_reduce` 等分块归约接口，并确保归约操作满足算法所需的结合、交换及类型闭包要求。

日志输出即便由内部锁保护，也会引入非确定顺序和串行瓶颈。需要调试时可让每个元素写入独立槽，算法完成后按索引顺序统一输出。

### 函数对象副本与元素访问

实现可以复制函数对象并在不同执行代理中调用副本。把可变计数器直接作为 Lambda 值捕获，只会得到若干彼此独立且结果难以汇总的状态；引用捕获共享计数器又会形成竞争。归约应通过算法的组合接口表达，不应依赖某个函数对象实例恰好处理一整块数据。

元素函数不得让一次调用以不受允许的方式修改另一次调用要读取的元素。即使两个迭代器位置不同，代理对象、压缩位容器和用户自定义迭代器也可能共享底层字。能安全并行写普通 `vector<T>` 不等于所有满足表面迭代器语法的范围都具备相同存储独立性。

策略重载通常对迭代器提出比顺序重载更强的类别要求，以便划分工作。调用前应读取具体算法声明，特别是输入迭代器的一次通过语义、输出范围容量和重叠规则。并行执行不会替调用方补足目标范围或检查越界。

## `reduce` 与传统 `accumulate`

`accumulate` 明确执行左折叠，适合顺序相关或非结合操作。`reduce` 允许以未指定分组顺序组合元素，以便树形并行归约；即使使用某些策略，结果也不应依赖固定括号结构。减法、字符串的非对称拼接等通常不适合作为归约操作。

`transform_reduce` 把元素转换和归约融合，避免显式中间容器，并可表达点积。扫描算法则产生每个前缀的归约结果，包含式与排除式版本对当前元素是否计入输出位置有不同定义。

数值代码若要求逐位可重复，应选择固定求和策略，或使用补偿求和、分箱等专门算法。单纯从 `accumulate` 换为并行 `reduce` 可能改变舍入路径。

### 操作闭包与初始值类型

归约实现可能先组合两个输入元素、两个部分结果，或输入元素与初始值，因此二元操作需要对标准列出的组合均可调用，并把结果留在可继续归约的类型域中。仅能执行 `Result op(Element)` 而不能组合两个 `Element` 或两个 `Result` 的操作，可能适用于手写左折叠，却不满足 `reduce` 的重排模型。

初始值还决定结果类型和一些重载解析。以整数 `0` 对浮点范围归约会把计算限制或转换到并非期望的类型路径，应传入 `0.0` 或明确领域累加器。对大对象，合并成本和临时对象移动也会决定树形归约是否真正有利。

扫描算法与归约共享结合性要求，但还要写每个前缀结果。`exclusive_scan` 在首个输出位置使用初始值，当前输入从后续位置开始影响结果；`inclusive_scan` 的当前元素包含在对应前缀中。边界测试应覆盖空范围和单元素范围。

## 性能模型

并行化增加任务切分、调度、同步和缓存一致性成本。只有工作量、元素数量和计算/内存比例足够时才可能加速。错误共享会让不同核心反复争用同一缓存行；内存带宽饱和也会限制扩展。

随机访问和连续存储通常更利于分块与向量化，但算法只承诺其签名规定的迭代器要求，不承诺特定调度策略。链表遍历、分支密集回调或极小元素操作可能无法摊薄调度成本。

基准测试应包含预热、真实输入分布、不同数据规模和目标机器核心数，并验证输出而不是只记录耗时。还要确认标准库后端是否需要额外运行库；某些 libstdc++ 版本借助外部并行后端，部署和链接配置会影响可用性。

### 前进保证与阻塞操作

执行代理能够获得何种前进保证取决于策略和实现。尤其在允许无序交错的执行中，不应假定一个调用会持续运行到释放另一个调用等待的锁。回调里的自旋等待、条件变量、线程局部单例初始化和内存分配都要按目标策略允许的操作重新审计。

`par` 下使用锁虽不必然不合法，却常把算法变成受锁保护的串行循环，并引入线程池任务与应用锁的依赖环。若每个元素需要访问共享服务，先分批准备只读快照或输出独立命令，算法结束后再串行提交，通常更容易证明进展与性能。

并行策略调用在返回前完成算法语义要求的工作，但这不等于提供跨算法调用的持久工作组身份。不能把一次调用的线程局部缓存设计成下一次调用必然复用的分片，也不能依据观察到的线程数分配固定索引数组。

## 可移植性与工程落地

C++17 规定 API，不意味着所有同年代标准库都完整实现。编译器前端支持 `-std=c++17` 与 `<execution>` 后端成熟度是两件事。仓库将此示例限定 GCC 参考任务，正是把工具链边界显式纳入验证。

引入策略重载的推荐顺序是：先让传统顺序算法正确且无隐藏副作用；为回调建立线程安全和异常契约；使用 `seq` 验证重载；再基准 `par`；只有操作满足更严格约束时才尝试 `par_unseq`。每一步都运行竞态检测和结果一致性测试。

## 示例与工程流程

示例使用 `seq` 验证策略重载接口及确定输出。迁移到 `par` 前，应先保证回调纯净和元素独立，再用真实数据基准测试顺序与并行版本，并在目标标准库上确认后端依赖和部署配置。

## 策略与算法速查

| 设施 | 关键保证/风险 |
| --- | --- |
| `execution::seq` | 顺序执行策略，不等于所有算法都有固定访问次序 |
| `execution::par` | 允许多线程并发调用元素函数 |
| `execution::par_unseq` | 还允许无序交错/向量化，禁止不安全阻塞操作 |
| 策略选择 | 是实现许可，不承诺一定创建线程 |
| 回调异常 | 标准策略重载中常导致 terminate |
| `reduce` | 允许重组括号，操作需适合归约 |
| `transform_reduce` | 融合转换与归约，避免中间容器 |
| `inclusive_scan` | 当前元素计入对应前缀结果 |
| `exclusive_scan` | 对应位置先使用此前累积/初值 |
| 浮点结果 | 分组改变可能导致舍入差异 |

## 并行算法专项审查问题

- 回调是否只访问当前独立元素或已证明的归约状态？
- `par_unseq` 回调是否含锁、分配、I/O 或不安全阻塞？
- 回调抛异常导致 terminate 是否符合错误策略？
- 原地输入输出范围的重叠是否由具体算法允许？
- reduce 操作是否对所有部分结果组合封闭且适合重排？
- 浮点逐位可重复是否是硬需求？
- 原子共享计数是否成为缓存行瓶颈？
- 算法输入规模是否足以摊薄任务调度成本？
- 标准库并行后端的链接/部署依赖是否确认？
- 基准是否验证输出并覆盖真实规模和机器核心数？
